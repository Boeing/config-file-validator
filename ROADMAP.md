# Roadmap

## v3.0 — Formatting (RC)

Syntax + schema + formatting in one tool.

- `cfv format .` checks formatting across JSON, JSONC, YAML, TOML, XML, HCL, INI, Properties, ENV
- `cfv format --fix .` rewrites in-place
- `cfv format --diff .` previews changes
- Per-format config in `.cfv.toml`
- Binary renamed to `cfv`, subcommand-based CLI
- `cfv check --fix` auto-fixes JSON trailing commas and schema type coercion

## v3.1 — Stable

Bug fixes and feedback from the RC, plus three infrastructure improvements:

### EditorConfig as base layer for `.cfv.toml`

When `.cfv.toml` exists, `.editorconfig` properties (indent_style, indent_size,
end_of_line, insert_final_newline) fill gaps that `.cfv.toml` doesn't explicitly
set. `.cfv.toml` wins when both specify a value.

**Behavior:**
- cfv reads `.editorconfig` using the same walk-up + merge semantics as today
- For each property: if `.cfv.toml` sets it (at global or per-format level) → cfv.toml wins
- If `.cfv.toml` does NOT set it → editorconfig value fills the gap
- Matches Biome/prettier: editorconfig is a universal baseline, tool config overrides

**Implementation:**
- Change Tier 1 resolution from "defaults → .cfv.toml → CLI" to "defaults → .editorconfig → .cfv.toml → CLI"
- The `applyFormatOptions` function already uses pointer/nil semantics for "set vs unset" — editorconfig fills nil slots, cfv.toml overwrites all
- Add tests: .cfv.toml + .editorconfig coexist, cfv.toml wins on overlap, EC fills gaps

**Why deferred from 3.0:** Keeps 3.0's mental model maximally simple — ".cfv.toml means you've migrated completely." Adding EC back in requires clear documentation of the interaction, which is better done after the base model is proven.

### `cfv migrate`

One-shot command that reads existing tool configs and generates a `.cfv.toml`.

```shell
cfv migrate                    # auto-detect and convert
cfv migrate --from=prettier    # explicit source
cfv migrate --dry-run          # show what would be generated without writing
```

**What it reads:**
- `.prettierrc` (all supported variants) → `[format]` and `[format.json]`, `[format.yaml]`
- `taplo.toml` → `[format.toml]`
- `.yamlfmt` → `[format.yaml]`
- `.editorconfig` → `[format]` (universal properties)

**Mapping tables:**

| prettier | .cfv.toml |
|----------|-----------|
| `tabWidth: 4` | `indent = 4` |
| `useTabs: true` | `indent-style = "tab"` |
| `printWidth: 100` | `max-line-width = 100` |
| `singleQuote: true` | `quote-style = "single"` (under `[format.yaml]`) |
| `trailingComma: "all"` | `trailing-commas = "all"` (under `[format.jsonc]`) |
| `endOfLine: "crlf"` | `line-ending = "crlf"` |

| taplo | .cfv.toml [format.toml] |
|-------|-------------------------|
| `indent_string = "    "` | `indent = 4` |
| `column_width = 120` | `max-line-width = 120` |
| `reorder_keys = true` | `sort-keys = true` |
| `trailing_newline = false` | `final-newline = false` |
| `crlf = true` | `line-ending = "crlf"` |
| `array_trailing_comma = false` | `trailing-commas = "none"` |

| yamlfmt | .cfv.toml [format.yaml] |
|---------|-------------------------|
| `indent: 4` | `indent = 4` |
| `line_ending: crlf` | `line-ending = "crlf"` |
| `max_line_length: 120` | `max-line-width = 120` |

**Output:**
- Writes `.cfv.toml` to the current directory
- Includes a comment header: `# Generated by cfv migrate from .prettierrc — review and commit`
- Reports what was read: "Read .prettierrc (tabWidth:4, printWidth:100, singleQuote:true)"
- Reports what was NOT mapped: "Skipped: bracketSpacing (not supported), overrides (not supported)"
- Does NOT delete the source config file — user does that manually after review

**Error handling:**
- If `.cfv.toml` already exists → error, refuse to overwrite (use `--force` to override)
- If no source config found → error, "no .prettierrc, taplo.toml, or .yamlfmt found"
- If source config is malformed → error with path and parse error

**Modeled after:** `biome migrate prettier --write`

### Ecosystem CI (formatter regression detection on PRs)

Automated system that formats real-world repos with both the base branch and the
PR branch, then reports what changed. Runs on every PR that modifies formatter
code. Modeled after Ruff's `ruff-ecosystem`.

**What it does:**

```
1. Detect: PR touches pkg/formatter/** → trigger ecosystem check
2. Build: compile cfv from main (baseline) and PR branch (comparison)
3. Format: run both binaries on a fixed set of real-world repos
4. Diff: compare outputs file-by-file
5. Report: post markdown summary as PR comment
```

**Repos (same as parity suite):**
ansible, argo-cd, compose, hugo, next.js, poetry, prettier, react, ripgrep,
rust-analyzer, uv, vscode

**Report format (posted as PR comment):**

```markdown
## Ecosystem Formatting Check

**3 files changed** across 12 repos (487 files tested)

### Changes

| Repo | File | Diff |
|------|------|------|
| next.js | packages/next/tsconfig.json | [view diff](#) |
| vscode | extensions/git/package.json | [view diff](#) |
| rust-analyzer | Cargo.toml | [view diff](#) |

### Stability
✅ All formatted files are idempotent (format twice = same result)
✅ No files that previously matched now differ (no regressions)
```

**Implementation:**

- GitHub Action workflow (`.github/workflows/ecosystem.yml`)
- Triggered on PRs that modify `pkg/formatter/**`
- Uses a pre-built Docker image with Node.js (for prettier comparison) and
  the 12 repos pre-cloned (cached in the image to avoid clone time)
- Runs in ~3-5 minutes (format ~500 files with two binaries)
- Posts results via `actions/github-script` or a lightweight Go binary

**Key design decisions:**

- **Triggered, not always-on.** Only runs when formatter code changes.
  Saves CI minutes on docs/tests/cli-only PRs.
- **Reports changes, doesn't block.** An intentional formatting change should
  NOT fail CI. The report shows WHAT changed so reviewers can decide if it's
  expected. Only blocks if idempotency fails or a previously-passing file
  regresses.
- **Repos are cached.** The Docker image includes shallow clones. `git pull`
  at runtime brings them current. No 12 × full clone per run.
- **Both binaries run in the same environment.** Eliminates "works on my machine"
  differences.

**Stability checks (block PR if violated):**
1. Every formatted file must be idempotent (format twice = same)
2. No file that matched with the base branch should differ with the PR branch
   (regression detection — new diffs are OK, lost matches are NOT)

**What this replaces:**
- Manual `~/.cfv-parity/run` before merge
- "Trust me, parity is still 99.5%" in PR descriptions
- The risk of merging a formatter change without knowing its real-world impact

**Why deferred from 3.0:** Requires GitHub Actions infrastructure, Docker image
build pipeline, and caching setup. The manual parity suite serves the same purpose
for the initial release. Ecosystem CI becomes critical once multiple contributors
are modifying formatters — you can't rely on one person's local parity run.

### P7: JSONC inline object with block comment

`{/*comment*/"K":"V"}` should stay inline as `{ /*comment*/ "K": "V" }` but cfv
expands to multiline. Also `/* comment */{` missing space before brace.

**Root cause:** `inlineValueLength` rejects objects with ANY comment in
`BeforeExtra` (returns -1 → object can't be inlined). The inline formatting loop
also overwrites `BeforeExtra` without preserving comment content. Top-level comment
spacing is a separate issue in the serialization path.

**Why deferred:** Fix requires coordinated changes to 3 functions. During 3.0
implementation, the fix exhibited whack-a-mole pattern (each fix uncovered the
next problem). Needs proper design — likely a `formatInlineObjectWithComments`
code path that handles comment placement within the inline format.

**Impact:** 1 file in prettier's JSONC test suite. 0 files in the 12-repo parity
suite. No real-world config files use this pattern (block comment inside an inline
single-line object).

**Fix approach (for 3.1):**
1. `inlineValueLength`: distinguish single-line block comments (`/*...*/` without
   `\n`) from multi-line. Single-line → allowed inline, add their length to total.
2. Inline format loop: when `BeforeExtra` has a single-line comment, render as
   `" /*comment*/ "` instead of overwriting with `" "`.
3. Top-level comment serialization: ensure space between trailing `*/` and `{`.

## v3.2 — Security Validation

Evaluate config files against community-maintained security rules using embedded OPA.

**User experience:**

```shell
cfv check --security .
cfv check --security --fix .
```

**How it works:**

- OPA embedded as a Go library (no external binary)
- Rules sourced from trivy-checks (500+ existing rules for K8s, Docker Compose, GitHub Actions, Terraform)
- File type identification via content inspection (apiVersion+kind → K8s, services: → docker-compose, path-based → GitHub Actions)
- Same pattern as `--schemastore` — cfv is the engine, the community owns the rules

**Severity gating:**

Only HIGH/CRITICAL block CI by default. Configurable via `.cfv.toml`:

```toml
[security]
fail-severity = "high"
```

**Baseline mode:**

Acknowledge pre-existing issues so day-one adoption isn't overwhelming:

```shell
cfv check --security --init .    # baseline existing state
cfv check --security .           # only new violations reported
```

**Auto-fix:**

Where a safe default exists (remove privileged: true, scope permissions, add resource limits), `--fix` applies it.

**Rule sources:**

| Source | Description |
|--------|-------------|
| Bundled | Curated subset shipped with the binary. Offline-capable. |
| Remote | Fetch latest from rule repo, cache locally. Optional. |
| Local | `--security-rules=path/` for custom/corporate policies. |

**Open questions:**

- Binary size impact (~15-20MB for OPA) — acceptable?
- Should `--security` default to on in a future major version?
- Rule customization (disable specific rules without a full baseline)
- Cross-file rules (e.g., "no NetworkPolicy for this namespace") — in scope or out?
